## Morz orchestrator engine: planner brain choice, NLâ†’spawn-planâ†’approveâ†’dispatch mechanics, run-state machine, and the exact mechanics of Manual / Assisted / Orchestrated modes

**Summary:** The orchestrator should run ON the user's own installed Claude Code CLI in headless bidirectional mode (`claude -p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio`), not the embedded Agent SDK and not a hand-rolled API loop. This is now the only compliant subscription path: Anthropic's Feb 19 2026 policy update bans consumer OAuth tokens in third-party products and states the Agent SDK requires an API key, while Anthropic staff explicitly confirmed (April 2026) that spawning the real `claude` binary as a subprocess is permitted; since June 15 2026 such `claude -p` invocations draw from a separate "Agent SDK credit pool" on subscriptions, which Morz's rate-limit meters should track as its own meter. The raw stream-json control protocol is fully reverse-documented (Roasbeef/claude-agent-sdk-go cli-protocol.md): NDJSON envelopes `system/init` (with a `capabilities` array for feature detection), `assistant`, `user`, `result`, plus bidirectional `control_request`/`control_response` multiplexed by `request_id` carrying `initialize`, permission (`can_use_tool`), `interrupt`, `set_permission_mode`, `hook_callback`, and `mcp_message` subtypes â€” so Morz writes one ~600-line protocol client and reuses it as both the planner driver and the Claude agent adapter. The NLâ†’team pipeline is: user intent â†’ planner session runs with read-only tools plus Morz MCP planning tools â†’ planner emits a typed SpawnPlan JSON (validated with `--json-schema`/structured output) â†’ rendered as an editable plan card â†’ explicit user approval stores a plan hash â†’ dispatcher creates git worktrees, allocates $PORTs, and spawns per-CLI adapters (Codex `exec --json` with stdin closed, agy via PTY bracketed-paste injection, OpenCode `serve` HTTP+SSE), refusing to spawn anything not in the approved plan. Each agent runs a persisted state machine (QUEUEDâ†’SPAWNINGâ†’RUNNINGâ†’BLOCKED_PERMISSION/BLOCKED_QUESTION/RATE_LIMITEDâ†’REVIEWâ†’DONE/FAILED/CANCELLED) fed by structured events â€” Claude stream-json `result` and `control_request`, Codex `thread.started/turn.started/item.completed/turn.completed/turn.failed` JSONL, Claude Code hooks `Notification` (`permission_prompt`, `idle_prompt`) and `Stop` for user-launched sessions, ANSI-stripped scrollback heuristics only for agy. The three modes are additive service layers on one engine: Manual runs only PTY-host + terminal UI + SQLite persistence (zero background LLM calls, zero watchers); Assisted starts the event-tap (CLI detection, hook-based state reporting over a named pipe gated on a MORZ_PANE_ID env var), the Morz MCP server, the message bus, routing suggestions, and one-click handoff chips â€” but never launches or types into a CLI without a click; Orchestrated adds the planner session, spawn plans, worktree isolation, the task board with atomic claim, scoped watchdog auto-responders, and bounded review loops. Dialing down mid-run is non-destructive: orchestratedâ†’assisted stops the dispatcher and converts pending auto-handoffs into suggestion chips while agents keep running; â†’manual detaches all services and leaves plain terminals, with all state in SQLite so dialing back up re-attaches.

- **Planner brain: user-owned Claude Code CLI headless vs embedded Agent SDK vs own API loop** => Run the orchestrator ON the user's installed `claude` CLI via the raw stream-json bidirectional protocol as the default; offer the Agent SDK (@anthropic-ai/claude-agent-sdk) as an alternate driver behind the same interface for users who configure ANTHROPIC_API_KEY. Never build your own bare-API agent loop â€” you'd re-implement tools, context management, and compaction that Claude Code already ships.
  HOW: Spawn `claude -p --input-format stream-json --output-format stream-json --verbose --permission-prompt-tool stdio` (stream-json output silently requires --verbose; add --include-partial-messages for token-level streaming into the orchestrator panel). - **NL â†’ spawn-plan mechanics (how intent becomes a team)** => Planner runs in a read-only 'plan phase' with Morz MCP planning tools, and must emit a schema-validated SpawnPlan JSON â€” never free text that Morz regex-parses.
  HOW: The planner session is configured with permission mode `plan` (or an allowedTools whitelist of Read/Grep/Glob plus Morz MCP tools `list_spaces`, `list_agents`, `read_pane`, `read_task_board`) so planning can inspect the repo and running panes but cannot write. - **Approve â†’ dispatch gate (the assist-don't-take-over enforcement point)** => Approval is a hard cryptographic-ish gate, not a UI nicety: the dispatcher only spawns from a stored, hashed, user-approved plan, and every spawned resource is tagged with the plan/run id for reversibility.
  HOW: The plan card is editable (change CLI, model, role, delete an agent, edit launch prompt) â€” edits mutate the SpawnPlan object, and Approve stores the plan JSON + SHA-256 hash + timestamp in SQLite (`runs` table). - **Structured launch prompt format** => One template, rendered per agent, with a machine-readable completion contract â€” sent through each adapter's native channel, never pasted as loose prose.
  HOW: Sections: ROLE (one line), OBJECTIVE (task titles + DoD checks verbatim), CONTEXT (worktree path, branch, $PORT, relevant file paths from the plan), BOUNDARIES (what NOT to touch; other agents' task ids), COMMUNICATION (exact Morz MCP tool names: `claim_task(id)`, `post_to_blackboard(msg)`, `consult(brain, question)`, `report_done(taskId, summary)`), and OUTPUT CONTRACT (a JSON schema for the final report). - **Run-state machine (per agent + per run)** => Two explicit machines persisted in SQLite with an append-only event log: agent states QUEUED â†’ SPAWNING â†’ RUNNING â†’ {BLOCKED_PERMISSION | BLOCKED_QUESTION | RATE_LIMITED} â†’ RUNNING â†’ REVIEW â†’ {DONE | FAILED | CANCELLED}; run states DRAFT â†’ PROPOSED â†’ APPROVED â†’ DISPATCHING â†’ RUNNING â†’ MERGING â†’ {DONE | ABORTED}. ## Morz backend: PTY-host + terminal wiring (node-pty/ConPTY + xterm.js) with Morz-styled command blocks and per-CLI presentation strategy

**Summary:** Copy VS Code's terminal backend wholesale: node-pty (ConPTY on Windows) running in a dedicated PTY-host process, spawned as an Electron utilityProcess so it gets Node.js APIs plus MessagePortMain channels straight to the renderer â€” bypassing main-process IPC hops for hot terminal data. Flow control is two-layer: node-pty's `handleFlowControl:true` (XON/XOFF, PAUSE='\x13'/RESUME='\x11') at the pty, plus VS Code's ack-based scheme where the renderer acknowledges every N bytes and the PTY-host pauses when unacked bytes exceed a high watermark â€” this is what stops a token-streaming Claude from flooding xterm.js. Command blocks come from shell-integration escape sequences: auto-inject a PowerShell/bash/zsh script at spawn (VS Code-style arg/env injection) that emits OSC 133 A/B/C/D (prompt-start / prompt-end / pre-exec / exit-code) plus a VS Code-633-style private Morz OSC channel for exact command line and cwd, with a per-session nonce to stop untrusted agents spoofing block boundaries; render blocks via xterm.js `registerMarker()` + the Decorations API so block chrome floats over one continuous buffer instead of splitting output into DOM chunks. Critically, Claude Code does NOT emit OSC 133 (open issues anthropics/claude-code #32635, #26235), so blockifying its interactive TUI by escape parsing is impossible today â€” the per-CLI strategy is: shells get OSC-133 blocks; interactive AI TUIs (Claude Code, Codex TUI, agy) get "framed full-TUI mode" â€” the raw xterm.js grid rendered inside Morz pane chrome with the graphite/quartz/bronze palette mapped into xterm's ITheme (16 ANSI colors + background/foreground), which is exactly Warp's alt-grid answer; and orchestrated/headless agent lanes get true structured blocks by driving `claude -p --input-format stream-json --output-format stream-json --include-partial-messages` and `codex exec --json` (JSONL events â†’ native React block components, no terminal emulation at all). Mode switching is driven by xterm.js `buffer.onBufferChange` (alternate-screen enter/exit via DECSET 1049) plus a known-TUI process registry, since Ink-based CLIs like Claude Code redraw in the normal buffer: normal buffer = block UI, TUI detected = full-TUI frame. Agent-state (working/blocked/idle/done) detection is layered: OSC 133 D exit codes for shells; Claude Code hooks (Stop/Notification/UserPromptSubmit/PreToolUse writing to a Morz named pipe â€” Morz auto-installs a session-scoped hooks config); JSONL events for Codex; and for dumb CLIs like agy, output-quiescence timers plus regex over an ANSI-stripped scrollback tail (spinner glyphs, y/n prompts) with bracketed-paste keystroke injection as the only input path. Session restore uses @xterm/addon-serialize snapshots plus SQLite-persisted block metadata, with VS Code's reviveTerminalProcesses pattern so PTYs owned by the PTY-host survive window reloads and PTY-host crashes don't take down the UI. Pin node-pty to VS Code's Electron/Node ABI and enable node-pty 1.1's `useConptyDll` option to ship a modern conpty.dll instead of relying on the OS-installed one.

- **Where PTYs live: process architecture** => Dedicated PTY-host as an Electron utilityProcess (not child_process.fork), with MessagePortMain channels wired directly rendererâ†”PTY-host.
  HOW: Main spawns `utilityProcess.fork('ptyHost.js')` once at startup; for each new pane the renderer asks main for a channel, main creates a `MessageChannelMain` and posts one port to the PTY-host (via `child.postMessage({type:'new-pty', opts}, [port1])`) and the other to the renderer via `webContents.postMessage`. All onData/write/resize traffic then flows rendererâ†”ptyHost directly, skipping the main process â€” this is the perf reason utilityProcess beats fork (fork can't transfer MessagePorts to renderers). Inside ptyHost: `pty.spawn(shell, args, {cwd, env, cols, rows, useConpty: true, useConptyDll: true, handleFlowControl: true})`; batch onData events (VS Code batches ~5ms windows into larger chunks because ConPTY data events can starve the event loop). Keep a per-pane ring buffer (raw bytes, e.g. 2MB) + an ANSI-stripped rolling text view in the PTY-host itself â€” this is what the orchestrator/reviewer and state-detectors read, and it survives renderer reloads. Crash isolation: if the PTY-host dies, main restarts it and calls a revive path (VS Code's reviveTerminalProcesses); if a single CLI floods, flow control throttles only that pane.
- **Flow control so a token-streaming agent can't freeze the UI** => Two layers: node-pty handleFlowControl at the pty + VS Code-style ack/watermark protocol between renderer and PTY-host.
  HOW: Layer 1: `handleFlowControl:true` makes node-pty intercept PAUSE='\x13'/RESUME='\x11' written to the pty (XON/XOFF) â€” implemented in node-pty's JS layer so it works identically over ConPTY. Layer 2 (the one that actually matters for xterm.js): the renderer counts bytes written into `term.write(chunk, cb)` and sends an ACK message back every CHUNK; the PTY-host tracks unacked bytes and calls `ptyProcess.pause()` past HIGH watermark, `resume()` when acks bring it under LOW. node-pty's pause/resume propagate real backpressure to the OS pty. Never rely on xterm.js's internal buffer alone â€” issue xtermjs/xterm.js#1918 documents that writing unbounded data to term.write() causes multi-second input latency and OOM. Also cap `term.options.scrollback` (e.g. 10k lines) since the PTY-host ring buffer is the real history.
- **Command blocks: mechanism and rendering** => Shell-integration escape sequences (OSC 133 + a Morz private OSC channel with nonce), rendered as marker-anchored decorations over ONE continuous xterm buffer â€” never split output into separate DOM/terminal instances per block.
  HOW: Auto-inject at spawn exactly like VS Code: for pwsh, launch with args that dot-source `morz-integration.ps1` (or env `MORZ_INJECTION=1` consumed by a profile snippet); for WSL bash/zsh source a script via `PROMPT_COMMAND`/`precmd`; for CMD use OSC 9;9 cwd reporting only (CMD can't do full 133). The script wraps `prompt` to emit `ESC]133;A ST` (prompt start), `ESC]133;B ST` (command start), uses PSReadLine hooks to emit `ESC]133;C ST` + `ESC]6553;CmdLine;<b64 cmd>;<nonce> ST` (exact commandline, VS Code's OSC 633;E pattern), and on return `ESC]133;D;<exitcode> ST` + `ESC]6553;Cwd;<path> ST`. The nonce (random per session, passed via env, validated in the parser) prevents a malicious agent's output from forging block boundaries or fake exit codes â€” non-negotiable given Morz's 'agent messages are untrusted' rule. Rendering: register an xterm.js parser hook `term.parser.registerOscHandler(133, ...)`, call `term.registerMarker(0)` at each A/C/D, and use `term.registerDecoration({marker, ...})` to paint Morz block chrome (rounded header with command + duration + exit-status pill; hover actions: copy command / copy output / re-run / send-to-agent). Block text extraction for 'copy output' = read buffer lines between the C and D markers. This is VS Code's exact architecture and it composes with scrollback, reflow, and search for free.
- **Per-CLI presentation strategy (the key question)** => Three-tier matrix: (1) shells â†’ OSC-133 blocks; (2) interactive AI TUIs (Claude Code, Codex TUI, agy) â†’ framed full-TUI mode (raw xterm inside Morz pane chrome + theme mapping); (3) orchestrated agent lanes â†’ no terminal at all: structured JSONL (stream-json / exec --json) rendered as native React agent-blocks.
  HOW: Tier 1 (pwsh/CMD/WSL in Manual mode): full block UI as above. Tier 2 (user interactively running `claude` in a pane): Claude Code does not emit OSC 133 â€” GitHub issues anthropics/claude-code #32635 and #26235 are open feature requests â€” and it's an Ink/React full-redraw TUI, so do NOT attempt to blockify it by escape parsing; instead render the untouched xterm grid inside the Morz pane frame: keep the pane header (agent identity pill, state dot, rate-limit meter), map Morz tokens into xterm's ITheme (background=graphite, foreground=quartz, the 16 ANSI slots tuned to the locked palette, selection/cursor=bronze) so the TUI 'wears' Morz colors â€” Claude Code's UI uses ANSI colors and respects terminal bg/fg, so this alone makes it look native. This is exactly Warp's 'alt-grid' answer for vim/htop. Tier 3 (Assisted/Orchestrated agents spawned by Morz): drive `claude -p --input-format stream-json --output-format stream-json --include-partial-messages --verbose` (NDJSON: system/init, assistant deltas, tool_use, result events) and `codex exec --json` through the Phase-2 adapter interface; render each turn/tool-call as a real Morz block component (collapsible tool calls, diffs, permission cards via canUseTool) â€” richer than any escape-sequence approach. agy stays Tier 2 PTY-only (its non-TTY empty-output bug is confirmed in your own docs) with keystroke injection: literal bytes, separate '\r', bracketed paste ESC[200~..ESC[201~ for multi-line.
- **Detecting normal-vs-TUI mode per pane** => Alternate screen buffer detection via xterm.js buffer API, plus a known-TUI process registry as the primary detector for agent CLIs.
  HOW: Subscribe to `term.buffer.onBufferChange(buf => mode = buf.type)` â€” DECSET 1049 (what vim/htop/lazygit emit) flips `buffer.active.type` to 'alternate'; on 'alternate' hide block chrome and switch the pane to framed full-TUI mode, restore block UI when it flips back to 'normal'. Caveat: Claude Code and other Ink-based CLIs often do NOT enter the alt screen (they redraw in the normal buffer with cursor-up + erase-line sequences), so alt-screen detection alone misclassifies them. Because Morz spawns every agent CLI itself, keep a small registry (claude, codex, agy, opencode, vim, lazygit, ...) and force TUI mode for panes it launched; alt-screen detection only needs to catch user-launched TUIs inside a shell. Optionally also watch OSC 133 silence: if a shell pane stops emitting prompt marks for a running foreground command that matches the registry, flip modes.
- **Agent-state (working/blocked/idle/done) detection** => Layered detectors, strongest-signal-wins: shell exit codes â†’ CLI-native hooks/JSONL â†’ output-quiescence + regex heuristics.
  HOW: (a) Shells: OSC 133;C = running, 133;D;<code> = idle with exit status â€” free from shell integration. (b) Claude Code interactive: Morz auto-writes a session-scoped hooks config (via --settings) wiring Stop, Notification (matchers: permission_prompt, idle_prompt), UserPromptSubmit, PreToolUse, SessionEnd to a tiny `morz-hook.exe` that writes one JSON line to a Morz named pipe (\\.\pipe\morz-agent-<paneId>) â€” Stopâ†’done/idle, Notification(permission_prompt)â†’blocked, PreToolUseâ†’working. Exact semantic state with zero scraping. (c) Codex exec --json / Claude stream-json lanes: state falls straight out of the event stream (tool_use=working, result=done, elicitation=blocked). (d) Dumb CLIs (agy): the PTY-host runs a quiescence timer (no output for ~2s AND cursor row stable â†’ idle) plus regex over the ANSI-stripped tail for known prompt shapes (`[y/n]`, `Press Enter`, `Continue?`, spinner glyphs â ‹â ™â£½ meaning working) â€” the amux/uzi watchdog pattern from your research doc, scoped per-agent, never a global auto-approve. Also parse OSC 0/2 title changes and OSC 9;4 progress as auxiliary signals. Publish the fused state on the internal bus for the sidebar pills and toasts.
- **Serialize/restore + PTY survival** => @xterm/addon-serialize snapshots + SQLite block metadata; PTYs owned by the detached PTY-host so window reload â‰  process death; accept lossy marker restore.
  HOW: On a debounce (~5s after output settles) and on window close, call `serializeAddon.serialize({scrollback: 1000})` and store the string + cwd + layout + block metadata rows (command, cwd, start/end line offsets, exit code, timestamps) in SQLite. Restore = create term, `term.write(serialized)`, then re-register markers from the persisted line offsets; accept that decorations inside the restored region are static/read-only â€” VS Code makes the same tradeoff. Because the PTY-host is a separate utilityProcess, a renderer reload just re-attaches: the renderer asks for the pane's port and the PTY-host replays the ring-buffer tail (track a per-pane byte counter so it replays only bytes-since-snapshot). For 'agents survive closing the window' (Herdr/OpenCode model), keep the PTY-host alive under a tray process â€” same code path, deferrable past 0.0.1.
- **Native module + Windows platform hygiene** => Pin node-pty to VS Code's tested Electron/Node ABI combo; enable useConptyDll; treat ConPTY quirks as known-issues to design around, not bugs to fight.
  HOW: Use `@electron/rebuild` in postinstall targeting the exact Electron version; mirror VS Code's node-pty version (they co-develop it â€” microsoft/node-pty ~1.1.x). Set `useConptyDll: true` so node-pty loads its bundled modern conpty.dll instead of the OS one (fixes long-standing resize/repaint bugs on older Win10/11 builds). Known ConPTY behaviors: it re-renders/re-wraps output on resize, so block boundaries stored as absolute line numbers drift â€” anchor blocks to xterm Markers (which reflow with the buffer) and persist offsets only for cold restore; ConPTY injects its own cursor-positioning sequences, so state detection must read the ANSI-stripped view, never raw-byte diffs. winpty fallback is unnecessary (Win10 1809+ baseline). PowerShell note: full shell-integration fidelity needs pwsh 7 + PSReadLine; Windows PowerShell 5.1 works degraded â€” default new panes to pwsh when installed.

**Missing ideas:**
- Spoofing defense: any agent can print ESC]133;D;0 and fake a successful block â€” the per-session nonce on the private OSC channel (VS Code does exactly this for OSC 633;E) must be in from day one, since Morz's core rule is 'agent messages are untrusted'.
- Ink-based CLIs (Claude Code) often do NOT use the alternate screen â€” alt-screen detection alone misclassifies them as blockable shell output; the known-TUI process registry (Morz spawns the CLI, so it always knows) is the load-bearing detector, not DECSET 1049.

- ConPTY reflows output on resize, so block boundaries stored as absolute line numbers silently drift â€” anchor everything to xterm Markers (which reflow with the buffer) and persist offsets only for cold restore.
- Claude Code hooks can emit terminalSequence output and Notification hooks have permission_prompt/idle_prompt matchers â€” exact blocked/idle semantics for the interactive TUI with zero scraping; almost nobody exploits this yet and it fits Morz's named-pipe bus perfectly.
- Theme mapping is cheap but high-impact: Ink TUIs inherit terminal bg/fg + 16 ANSI colors, so a well-tuned ITheme makes Claude Code look Morz-branded with zero protocol work; ship the base16/Ghostty theme mapper early since it's the same field-rename transform.
- Kitty keyboard protocol (CSI u): Warp supports it for full-screen apps; xterm.js support is partial â€” verify before promising perfect keybinding fidelity inside TUIs.
- Copy-on-select and 'send block to agent' both need the ANSI-stripped view aligned to marker ranges â€” build the stripped ring buffer with byte-offsetâ†”line mapping in the PTY-host once, and every consumer (orchestrator, reviewer, state detector, block copy) reads the same structure.
- stream-json event schema is under-documented and unstable (anthropics/claude-code issues #24594/#24596) â€” pin the CLI version per adapter and feature-detect via the system/init capabilities payload rather than assuming event shapes.

**Open questions:**
- Manual-mode default for `claude`: when the user types `claude` in a plain Morz shell pane, keep it pure framed-TUI (most faithful to assist-don't-take-over) or offer an opt-in 'agent lens' toggle that relaunches it under stream-json with the native block renderer? (Product-behavior call.)
- Should Morz auto-install the Claude Code hooks config for state detection into the user's project settings, or only pass --settings on Morz-spawned sessions? Touching user config files is a trust/product decision.
- Default shell for new panes on Windows: pwsh 7 (full OSC 133 integration) vs the user's existing default (possibly PowerShell 5.1 / CMD with degraded blocks)?
- PTY survival scope for 0.0.1: PTY-host dies with the app (simple) vs tray-resident so agents survive window close (Herdr/OpenCode model, more plumbing)?
- Private OSC number: adopt VS Code's actual 633 sequences for ecosystem compatibility (some tooling already emits them) vs a Morz-owned number to avoid colliding with VS Code's evolving semantics?

## In-app IDE (CodeMirror 6 pane) + external editor handoff for Morz pre-alpha 0.0.1

**Summary:** Morz's ctrl-click-path-to-side-preview is already specced in MORZ-Research-and-Vision.md section 4.6 (OSC-8 morz:// links + verified-on-disk regex link provider, file:line:col grammar) and BUILD-BREAKDOWN.md Phase 1; this research fills in the editor pane itself and the exit ramp to real IDEs. Warp validates the exact scope: its built-in Code Editor (docs.warp.dev/code/code-editor) is deliberately NOT an IDE â€” syntax highlighting for ~25 languages, tabbed file viewer, find/replace, Vim keybindings, file tree, opened by clicking a file path in terminal/agent output â€” positioned for "fine-grained edits to agent-generated diffs," with LSP explicitly absent; Morz should copy that scope with CodeMirror 6. Concretely: @codemirror/language-data ships LanguageDescription metadata for 100+ languages with LanguageDescription.matchFilename(languages, name) and lazy .load() dynamic imports, so one small core (~200KB) covers every language the agents touch without bundling all grammars; a single custom Slate theme is built with EditorView.theme({...},{dark:true}) plus a HighlightStyle whose colors read the existing tokens.css CSS variables (var(--...) works in CM theme specs), so terminal and editor share the graphite/quartz/bronze palette automatically. The file service is a main-process module over typed IPC: fs.readFile/atomic write-temp-then-rename save, chokidar v4 watch on open files, mtime-based conflict detection with a reload/overwrite banner â€” critical in Morz because agents rewrite files under the editor constantly. Reveal file:line:col is a dispatch of EditorSelection.cursor(doc.line(line).from + col-1) plus EditorView.scrollIntoView(pos,{y:'center'}) and a transient line-highlight decoration. External handoff is protocol URLs via Electron shell.openExternal: vscode://file/{abs-path}:line:col is officially documented (VS Code CLI docs, issue #27997); cursor://file/{path}:line:col works because Cursor is a VS Code fork (community-confirmed, no official doc â€” verify at runtime); Windsurf registers windsurf:// but the file/line form is unverified, so the robust fallback for all VS Code forks is the CLI `code|cursor|windsurf -g {file}:{line}:{col}`; JetBrains needs Toolbox and uses jetbrains://{toolTag}/navigate/reference?project={name}&path={relpath}:{line}:{col} (or idea://open?file=&line=, or `idea64.exe --line N path` CLI) â€” defer it. Detect installed targets on Windows by probing HKEY_CLASSES_ROOT\vscode, \cursor, \windsurf registry keys (protocol registration) plus CLI-on-PATH. For hover/go-to-def, the official @codemirror/lsp-client (by CodeMirror's author, sponsored by zoo.dev) now supports completion, hover, signature help, go-to-def, rename, references and diagnostics over a pluggable Transport â€” the right later-phase choice over the older FurqanSoftware/marimo codemirror-languageserver WebSocket packages â€” but LSP should be entirely out of pre-alpha scope, exactly as Warp shipped without it.

- **Editor engine and language support** => CodeMirror 6 (already chosen in the stack) with @codemirror/language-data for lazy per-language loading; do NOT bundle individual @codemirror/lang-* packages by hand.
  HOW: Core extensions: @codemirror/view, @codemirror/state, @codemirror/language, @codemirror/commands, @codemirror/search (openSearchPanel for find/replace), lineNumbers(), highlightActiveLine(), bracketMatching(), indentationMarkers optional. Wrap the result in a Compartment so language can be reconfigured when the same pane opens a different file.   HOW: Export morzEditorTheme = [EditorView.theme({'&': {backgroundColor: 'var(--surface-1)', color: 'var(--text-primary)'}, '.cm-gutters': {...}, '.cm-activeLine': {...}, '.cm-selectionBackground': {...}}, {dark: true}), syntaxHighlighting(HighlightStyle.define([{tag: tags.keyword, color: 'var(--syntax-keyword)'}, {tag: tags.string, color: 'var(--syntax-string)'}, ...]))]. - **File service (read/watch/save) architecture** => A single FileService in the Electron main process behind typed preload IPC; renderer never touches fs.   HOW: Save is atomic: write to `${path}.morz-tmp` then fs.rename over the original (same trick as the section-7 mailbox), and record the resulting mtime so the service can suppress the self-triggered chokidar event (echo suppression â€” otherwise every save fires a spurious 'external change' banner). Watch with chokidar v4 on exact open-file paths only (not directory trees â€” the explorer already watches roots), awaitWriteFinish: {stabilityThreshold: 150} so an agent mid-write doesn't stream half-files into the editor. Guard rails: refuse files >20MB and binary sniff (NUL byte in first 8KB) -> fall back to a hex/'open externally' placeholder.

  HOW: Clamp line to view.state.doc.lines, compute pos = doc.line(line).from + min(col-1, lineLength), then view.dispatch({selection: EditorSelection.cursor(pos), effects: EditorView.scrollIntoView(pos, {y: 'center'})}) and view.focus().   HOW: Use EditorState.readOnly.of(false) always; 'preview' is purely tab-lifecycle semantics: a subsequent ctrl-click replaces the current preview tab unless it is dirty or was pinned (double-click).   HOW: Primary: shell.openExternal(`vscode://file/${absPath}:${line}:${col}`) â€” officially documented (forward slashes fine on Windows; encodeURI the path, keep the drive-letter colon). ## Message bus + Morz MCP server implementation (Morz pre-alpha 0.0.1 backend)

**Summary:** The bus should be three layers behind one internal API: (1) a Maildir-style file mailbox (tmp/ â†’ fsync â†’ atomic rename into new/, DJB's lock-free protocol) holding human-readable JSON-frontmatter+Markdown messages under a project-local .morz/bus/ tree; (2) a Windows named-pipe push channel (Node `net.createServer().listen('\\\\.\\pipe\\morz-bus-<nonce>')`) that carries only NDJSON wake notifications and authenticated handshakes â€” payloads stay in files so a pipe crash loses nothing; (3) a SQLite task board (better-sqlite3, WAL, busy_timeout) where claiming is one atomic `UPDATE â€¦ WHERE id=(SELECT â€¦) AND status='ready' RETURNING *` compare-and-swap with DAG dependencies enforced by a NOT EXISTS subquery and lease-based reclaim. The critical architectural fact about the Morz MCP server: stdio MCP servers are spawned as child processes by each CLI, so `morz-mcp` must be a thin shim (official @modelcontextprotocol/sdk, McpServer + registerTool + Zod, StdioServerTransport) that connects back to the Morz main process over the named pipe and authenticates with a per-agent token from env â€” all state and all trust decisions live in Morz, never in the shim. Tools (post_to_blackboard, read_blackboard, claim_task, complete_task, consult, read_pane, open_file_in_preview, pick_element) get honest MCP annotations (readOnlyHint/destructiveHint) but the router enforces scopes server-side because annotations are only hints. Registration is mechanical per CLI: Claude Code via `.mcp.json` at the worktree root (mcpServers/command/args/env, supports ${VAR} expansion); Codex via `[mcp_servers.morz]` in config.toml with `startup_timeout_sec`/`tool_timeout_sec` (spawn each Codex agent with a per-agent CODEX_HOME to isolate config+identity); Antigravity via ~/.gemini/antigravity/mcp_config.json (IDE) or ~/.gemini/antigravity-cli/mcp_config.json (CLI) â€” though agy stays primarily PTY-driven; OpenCode via project opencode.json `"mcp": {"morz": {"type":"local","command":[...],"environment":{...}}}`, which being project-level makes per-agent env trivial. Handoff automation replaces the manual AGY_RESULTS.md pattern: post_to_blackboard(kind:'handoff') â†’ router stamps sender identity, persists to the target's mailbox, wakes it over the pipe, and the target's adapter injects a "read your handoff" prompt (MCP-capable CLIs) or a bracketed-paste brief (agy); in Assisted mode every dispatch is a propose-then-approve card in the orchestrator panel, honoring the control dial.

- **Mailbox directory layout + on-disk message format** => Project-local `.morz/bus/` using Maildir tmp/new/cur semantics per agent inbox, messages as JSON-frontmatter + Markdown body files, mirrored into a SQLite index for querying.
  HOW: Layout: `.morz/bus/agents/<agentId>/inbox/{tmp,new,cur}/`, `.morz/bus/blackboard/{tmp,new,cur}/` (broadcast), `.morz/bus/endpoint.json` (pipe name + nonce), `.morz/bus/tasks.db`. Delivery follows DJB's Maildir protocol exactly: write to `tmp/`, `fs.fsyncSync(fd)` the file handle (Windows can't fsync directories â€” file-level fsync + same-volume `fs.renameSync` into `new/` is the NTFS-safe equivalent), then rename; readers move `new/` â†’ `cur/` after processing, so a message is never seen half-written and no locks exist anywhere. Filename = `<epochMs>.<ulid>.<agentId>.md` (the Maildir `time.MusecPpid.host` analog, collision-free). File format: a `---` YAML frontmatter block with `{v:1, id:<ulid>, thread_id, task_id?, from, to:agentId|'blackboard', kind: status|handoff|question|answer|artifact|review_finding, priority, created_at, requires_ack:boolean, artifacts:[{type,path}]}` followed by a Markdown body â€” git-diffable and eyeball-able, which is the point. The bus daemon tails every `new/` dir with chokidar v4 as the poll fallback and inserts a row into a `messages` index table so the blackboard panel can query/filter without re-parsing files. Add `.morz/` to .gitignore by default (offer opt-in commit for audit trails).
- **Push channel: Windows named pipe protocol** => One `net` IPC server in the Morz main process at `\\.\pipe\morz-bus-<random-nonce>`; NDJSON frames; notifications-only (payloads stay in files); token handshake for identity.
  HOW: Node's net module implements IPC as named pipes on Windows: `server.listen(path.join('\\\\?\\pipe', projectHash, 'morz-bus'))`; the pipe vanishes when the owning process exits (unlike unix sockets, no stale-file cleanup) and `net.createServer()` handles multiple concurrent clients natively â€” one connection per agent shim. Because Windows named pipe names are machine-global and any local process can connect, do NOT trust the connection itself: generate a per-session nonce for the pipe name plus a per-agent random token, write both into `.morz/bus/endpoint.json` (pipe name) and each agent's env (`MORZ_AGENT_ID`, `MORZ_AGENT_TOKEN`), and require a first frame `{op:'hello', agentId, token, pid}` before any other op is accepted. Wire protocol is newline-delimited JSON: serverâ†’client `{op:'event', type:'msg.new'|'task.ready'|'task.unblocked', path?, taskId?}` and clientâ†’server `{op:'post'|'claim'|'complete'|'read'|'consult', reqId, ...}` with `{op:'result', reqId, ...}` replies. Keeping message bodies out of the pipe means a dropped connection degrades to chokidar polling of `new/` with zero data loss; shims reconnect with exponential backoff and re-hello (idempotent handshake, since CLIs restart their MCP children freely).
- **SQLite task board: schema, CAS claim, DAG dependencies** => better-sqlite3 in the bus daemon only (single writer), WAL + busy_timeout, atomic `UPDATEâ€¦RETURNING` claim with lease expiry, deps as an edge table with a NOT EXISTS readiness check.
  HOW: Schema: `tasks(id TEXT PK /*ulid*/, space_id, title, spec_md, status TEXT CHECK(status IN ('queued','ready','claimed','in_progress','review','done','failed','cancelled')), claimed_by, claim_expires_at INTEGER, priority INTEGER, wave INTEGER, dod_checks TEXT /*json*/, result_msg_id, created_at, updated_at)`; `task_deps(task_id, depends_on, PRIMARY KEY(task_id,depends_on))`; `messages(...)` index; `agents(id, space_id, cli, token_hash, scopes TEXT)`. Claim is the documented SQLite 3.35+ pattern â€” a single statement, no SELECT-then-UPDATE race: `BEGIN IMMEDIATE; UPDATE tasks SET status='claimed', claimed_by=:agent, claim_expires_at=:now+:lease WHERE id=(SELECT id FROM tasks t WHERE t.status='ready' AND t.space_id=:space AND NOT EXISTS (SELECT 1 FROM task_deps d JOIN tasks p ON p.id=d.depends_on WHERE d.task_id=t.id AND p.status!='done') ORDER BY priority DESC, created_at LIMIT 1) AND status='ready' RETURNING *; COMMIT;` â€” the trailing `AND status='ready'` is the CAS. On any taskâ†’done transition, run the unblock pass (`UPDATE tasks SET status='ready' WHERE status='queued' AND <same NOT EXISTS>`) and push `task.unblocked` events over the pipe. A 30s sweeper reclaims expired claims (`status='claimed' AND claim_expires_at < now` â†’ back to 'ready'), which handles crashed agents; `complete_task` only moves to 'review'/'done' after Morz itself runs the task's Definition-of-Done checks â€” an agent asserting success is never sufficient.
- **Trust boundary enforcement** => All authorization in the router (main process), keyed on the pipe-handshake identity; sender fields stamped server-side; MCP annotations used honestly but never relied on.

**Missing ideas:**
- Rate-limit meters in the mockup have no real data source: Claude exposes cost/tokens in stream-json result events and ~/.claude/projects JSONL (ccusage parses these), but Codex/agy/OpenCode need per-CLI strategies (Codex exec --json emits token counts; agy has nothing â†’ the meter must show 'unknown' honestly rather than fake data). Design the meter to accept 'no data' as a first-class state.
- ConPTY orphan processes: if Morz dies without closing pseudoconsoles, conhost.exe/OpenConsole.exe instances leak. Tag every child with a MORZ_SESSION env GUID and sweep-kill stale ones at startup â€” no competitor does this cleanly.
- Signing sequencing: an unsigned pre-alpha that later becomes signed breaks electron-updater trust and re-triggers SmartScreen; set up Azure Trusted/Artifact Signing before any build leaves the machine, or accept manual reinstalls.
- Windows Defender / AV false positives: an app that spawns PTYs, injects keystrokes, and writes many small files matches heuristic malware patterns; signing helps most, plus submit false-positive reports to Microsoft early and avoid packing the PTY host with bytenode-style obfuscation.
- Shell-environment fidelity: Electron apps launched from the Start Menu inherit a minimal environment; the PTY host must resolve the user's real PATH (spawn an interactive PowerShell once to capture env, like VS Code's shellEnv resolution) or CLIs installed via npm/pipx won't be found in Morz but will work in Windows Terminal â€” a classic first-impression killer.
- Keyboard/UX parity details that decide daily-driving: Ctrl+C must copy when a selection exists and send SIGINT otherwise (Windows Terminal behavior); Ctrl+V bracketed paste with multi-line paste warning; IME input for CJK in xterm.js needs explicit testing.
- E2E test harness: Playwright has first-class Electron support (_electron.launch) â€” build the torture suite on it from Slice 1 so 'limit-test it' is a repeatable npm script, not a manual ritual.
- License hygiene: Herdr is AGPL â€” document a clean-room policy (study behavior, never read source) now, since 'open vs closed' is still an open decision and AGPL contamination would foreclose options.
- Long-path and UNC handling on Windows (worktrees under deep paths, \\wsl$\ paths in the preview pane) â€” enable longPathAware in the app manifest and test >260-char repos once worktrees land.
- Multi-window is deferred, but the decision to put the PTY host in a window-independent utilityProcess (not per-window) is what keeps it cheap later â€” VS Code's shared-process lesson; don't let any slice sneak in window-scoped PTY state.
